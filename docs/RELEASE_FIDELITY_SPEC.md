# 发布保真规范

Nasti 的开发、验收和发布都以用户最后确认的代码和素材为基准。只实施用户授权范围内的改动。未经用户明确允许，任何人或自动化都不得替换、删减或改制基准中的代码、图标、启动画面、字标、人物图层、模型及其他素材。打包权限不包含修改设计或扩大代码改动范围的权限。遇到素材分发疑问或技术阻碍时，列明文件、原因和影响，请用户决定后再处理。

当前获准的发布调整如下。

- 清空发布曲库，并排除个人歌单、歌曲文件、封面、Vault、数据库、OAuth 凭据和本机配置。空曲库所需的运行时支持及独立测试数据属于此项。GitHub 主分支 README 可保留经用户允许的展示，展示资料不进入标签源码和安装包。
- 应用名称为 Nasti。Beta 区分使用设置中的版本号、构建版本元数据和 GitHub 发行版本，延续 beta 已有的数据目录和应用标识。
- 执行签名、公证、打包、校验和及发布说明所需的操作。以上流程继续使用同一份获准源码及素材。

每次发布都用 `docs/RELEASE_FIDELITY_SHA256SUMS` 核对定稿视觉文件和宿主图标。未经用户明确同意，不得为了让检查通过而改写基准哈希。由发布者审阅相对于确认基准的源码差异，并记录每一项差异的授权依据。

从干净的发布源码执行 `node scripts/verify-release-fidelity.mjs`。前端构建完成后，再传入生成目录进行第二次检查。签名后核对应用包图标、空曲库和版本，启动实际包检查 Dock 图标、开机画面及设置版本。公证并附上票据后，从 GitHub 匿名下载发布包，对照哈希、验证 Gatekeeper 并回读验收 Issue。

启用应用内更新的版本还应执行[更新资产与存储规范](NATIVE_STORAGE.md)。更新归档与 DMG 必须来自同一份已验收并公证的应用。
